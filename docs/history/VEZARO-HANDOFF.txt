VEZARO HEALTH MVP — SESSION HANDOFF
====================================

MISSION
-------
Build the MVP website for Vezaro Health, a US telehealth clinic run on an MSO/CPOM model,
using Guano through its MCP tools. This is Guano's first real client project, and there
are two equal jobs:
  1. Build as much of the brief as Guano can do properly.
  2. Log every place where Guano falls short in GUANO-FEEDBACK.md at the repo root.


CLIENT BRIEF (summary of the French original)
---------------------------------------------
- Design: premium, simple, reassuring, built for conversion, and inspired by modern US
  telehealth sites (Medvi, home.medvi.org) without copying its copy, layout, imagery or
  branding. Medical, American, mobile-first and responsive.
- Bask Health (headless, API-first) supplies all medical and operational infrastructure:
  EHR, prescriptions, payments, HIPAA. The agency builds none of that.
- Scope 1, public site: homepage, service pages, treatment pages, FAQ, legal pages,
  mobile navigation, CTAs and conversion funnels, analytics.
- Scope 2, subscription funnel: landing -> treatment choice -> questionnaire -> account
  creation -> payment -> handoff to Bask -> status tracking. Mobile-first, with minimal
  drop-off.
- Scope 3, questionnaire and Bask REST integration: API auth, POSTs, secure transmission,
  response and error handling, field mapping, webhooks, payment status,
  medical-validation status, and journey-state updates.


BUILD VS. ASSESS
----------------
BUILD in Guano:
- The public site (home, services, treatment pages, FAQ, legal shells, mobile nav, CTAs).
- The funnel as screens only (landing -> treatment -> questionnaire -> account -> payment
  -> confirmation -> status), with visual flow and navigation but no collection or
  sending of real data.

ASSESS only, don't build:
- All of brief section 3, and analytics.
- Write a "Bask Health integration — gap analysis" section in GUANO-FEEDBACK.md that
  covers every section-3 item: can Guano support it today, and if not, what's missing
  (server-side API calls with secret keys, webhook endpoints, per-user status pages,
  PHI-safe handling, ...).


HARD RULES
----------
- No API keys, secrets or third-party API calls in custom code or page markup.
- Guano forms never collect questionnaire answers, health information or payment details.
  Questionnaire screens show the fields, but they submit nowhere: the forms are never
  enabled.
- Don't change the agent policy, publish settings or integrations, and NEVER PUBLISH.
  Work in a draft named "Vezaro MVP" (the user confirmed this) and check with `preview`.
- No invented facts: no doctor names, credentials, testimonials, review counts, prices,
  medication claims or outcome statistics. Use marked placeholders: [PRICE],
  [PHYSICIAN NAME], [TESTIMONIAL — needs approved copy], [STAT — needs source].
- Legal pages (Terms, Privacy, HIPAA Notice of Privacy Practices, Telehealth Consent,
  Refund policy) get headings and structure only, with [LEGAL COPY REQUIRED] instead of
  text.
- Original US-English copy only.
- DON'T BYPASS, REPORT. If a tool refuses, errors, reports success for something that
  doesn't render in `preview`, or lacks a feature:
    - Don't work around it: no custom-code hacks, no hidden elements faking behavior,
      no duplicated structure, no repeated retries.
    - Don't fix Guano.
    - Log it, simplify or skip that piece, and continue.

DECISIONS MADE WITH THE USER
----------------------------
Palette:
  Mono + one accent.
    background  #F5F5F3  off-white
    surface     #FFFFFF
    ink         #0E0E0E
    soft        #E9E9E6
    muted       #6E6E6A
    accent      #9ED9C3  mint (CTA only)
  Declare these as semantic tokens first (background, foreground, card, muted,
  muted-foreground, accent, border, ...).
Type:
  Google Sans only, with no serif accent. Contrast comes from weight: light/regular
  headline with one bold word, like "Professional **bank** card".
Imagery:
  Free-license stock photos (Unsplash/Pexels: people, calm nature, neutral product
  shots) uploaded with upload_media so they're swappable later.
Treatments:
  Weight management, and Skin & longevity. Placeholders, with no claims or prices.
Funnel end:
  Screens only. Bask handoff and analytics go in the gap analysis.
Site-wide motion:
  Page transitions (fade preset), smooth/inertia scroll, and replay reveals
  (appearMode: replay), all set with update_settings.motion.
Size:
  Lean MVP, about 15 routes: Home, How it works, About/Clinicians, FAQ, 2 treatment
  pages from a collection, 5 legal shells, plus funnel screens.
Language:
  US English only. Spanish was never in the brief.
Analytics:
  Assess only. Custom code stays off.


DESIGN READING (agreed with the user)
-------------------------------------
The user's own notes: rounded and clean, LOTS of animation (reveal, hover, scroll),
premium and Awwwards-like, dummy content based on the brief.

Visual references:
1. Roco.bank: big light headline with one bold word, black pill buttons, fanned and
   tilted cards as the hero, a logo strip, floating avatar chips.
2. Mental-health "About us": centered pill section label, three photos fanned around a
   center one, a three-column stat row with thin dividers, a soft pill CTA.
3. Shyen "Connected": soft gradient glow at the top of a section, a large rounded
   full-bleed photo card, small pill tags, a horizontal card carousel inside it.
4. Shyen products: copy on the left and a big rounded product image on the right,
   numbered product tiles below, an outlined pill CTA.
5. Cereen: pill topic tags, a large rounded portrait card with frosted-glass stat
   overlays, a circular arrow "explore" button, a split Login/Register pill.

What they share: whitespace, large radii, pills everywhere, photos in rounded frames,
small frosted UI over photos, weight-contrast headlines.

Motion vs. conversion (agreed):
- Marketing pages get the expressive motion: staggered reveals, scroll-scrubbed card
  stacks, hover lift.
- THE FUNNEL STAYS CALM: clear progress, one question per screen, large touch targets,
  only subtle transitions.
- Motion never delays content or CTAs, and it respects reduced-motion.
- Stat rows and testimonials from the references become marked placeholders.

GUANO NOTES ALREADY LEARNED FROM get_guide
------------------------------------------
Workflow:
  get_status -> set_target -> update_settings (tokens, fonts, motion) -> list_components
  -> create_component {html} -> pages with set_page_html (whole page in one call,
  components as <Name />) -> edit_structure for local changes -> edit_elements batched
  (or pages:[...]) for media, icons, variants and bindings -> preview, and act on its
  warnings.

HTML subset:
- <button>, <a> and <label> are containers, so their words go in a <span>.
- Leaves are the headings, <p>, <span>, <option>, and <div data-type="text">.
  A <section> with bare text is refused.
- Icons are written <svg data-icon="name" /> (Lucide; check names with list_icons).
- Use data-ref on everything you'll come back to. Refs are refused inside instances.
- Fill instances with edit_elements {ref, part: "span[1]"}, or inline in the markup
  (content, src and alt only).
- href on a container makes the whole block clickable.

Forms:
- A form left un-enabled posts nowhere, which is exactly right for the questionnaire
  mock.

Styling:
- Tailwind classes; arbitrary values are allowed, arbitrary properties aren't.
- current: styles the active nav link inside a shared component.
- group + group-hover: for card hovers.
- Style <body> on every page (the default is white/black).
- The published body is a flex column, so full-bleed sections take w-full and an inner
  div uses mx-auto max-w-6xl px-6.

Design standards:
- One container width and one spacing scale.
- Consistent radius per kind of element.
- No layout shift on hover.
- Every control styled, with appearance-none plus a drawn chevron on selects, and
  visible focus rings.
- Entrances 200-400 ms: containers fade, small items move a few px, staggered.
- One overlay per kind, outside lists.
- No leftover unused effects.

Big payloads:
- Send them through htmlPath / editsPath / manifestPath / entriesPath (absolute paths;
  use the scratchpad).

Guide sections still to read before using each feature:
  components, nesting, slots, variants, icons, class-interactions, animations, sliders,
  forms, data, content, media, project-settings, current-tool-gaps.
